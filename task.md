New `PayrollPayment` model (amount, paidOn, note, createdAt) hanging off `PayrollRecord`, which already *is* one unique (employee, month) pair, so the FK carries both and an orphan payment for a month with no salary structure — and therefore no net to measure against — is impossible by construction. Status is **derived** in `services/payroll.js` from the payment sum, never a stored flag: `pending` (nothing paid) / `partial` (some paid, balance outstanding) / `paid` (sum reached the net), flipping by itself as instalments land. `PayrollRecord.paidOn` survives as a **derived cache** — the date the running total first reached the net — recomputed from the payment rows inside the same transaction on every write (`resettle()`), so the payslip PDF's single scalar can't drift from the rows behind it; recomputed wholesale rather than nudged, because a back-dated payment can settle a month *earlier* than before. Both chosen rules meet in one consequence worth stating: an overpaid month is settled, therefore locked, so a wrong payment is corrected by deleting it, not by editing the salary. Admin Payroll gained a per-month detail (net / paid / remaining + every payment) and a "Partially paid" badge; Employee Payroll and the PDF slip were updated to the same three states (the PDF previously printed "Payment pending" for a month with money already in it); one serialiser (`payrollShape`) feeds the admin list, the admin detail, the employee read and the slip so they cannot disagree.
